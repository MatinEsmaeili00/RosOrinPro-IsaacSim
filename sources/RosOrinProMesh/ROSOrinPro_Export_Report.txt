5. BLENDER -> UNREAL COORDINATE CONVERSION
------------------------------------------------------------------------------
   Blender scene = ROS REP-103 frame: right-handed, +X forward, +Y left, +Z up, 1 BU = 1 m.
   Unreal:                           left-handed,  +X forward, +Y right, +Z up, 1 uu = 1 cm.
   FBX file: UnitScaleFactor = 1 (cm), Up = +Z, Front = -Y, Coord = +X, right-handed.
   That is exactly Unreal's FBX import axis system (Z-up, -Y front), so the importer applies no
   axis rotation and only its right->left handed flip (Y -> -Y). Net mapping:
       position     : UE(x, y, z) cm = (100*x, -100*y, 100*z)  with ROS (x, y, z) in m
       orientation  : UE FRotator(Pitch, Yaw, Roll) = (-pitch, -yaw, +roll) of the URDF rpy, in degrees
       quaternion   : UE (X, Y, Z, W) = (-qx, qy, -qz, qw)
       joint axis   : UE axis = (-ax, ay, -az);  rotation = FQuat(UEAxis, q) with q straight from /joint_states
       /odom        : actor location = (100*x, -100*y, 100*z) of odom->base_footprint,
                      actor rotation = (-qx, qy, -qz, qw) of its quaternion.
   Driving a joint in Unreal:  Comp->SetRelativeRotation(RestRelativeQuat * FQuat(UEAxis, q))
   (RestRelativeQuat = the component's imported relative rotation; FQuat A*B applies B first).
   Mimic joints (gripper): q_child = multiplier * q_r_joint + offset (see table above).
   Import in Unreal with: Force Front X Axis = OFF, Convert Scene = ON (default), Convert Scene Unit = ON
   (no-op, file is already cm), Import Uniform Scale = 1.0, Transform Vertex To Absolute = OFF,
   Bake Pivot In Vertex = OFF, Combine Meshes = OFF. Use File > Import Into Level to get the hierarchy:
   one actor per URDF link (named like the link, attached like the URDF tree) under an identity
   'RootNode' actor that Interchange creates for the FBX scene root; static mesh assets are named
   SM_<link> (UE 5.8 Interchange appends '_001', e.g. SM_link1_001 - cosmetic).
   Drive base_footprint (or RootNode) from /odom. If you convert the actors to one Blueprint
   (Convert Selection to Blueprint Class), re-check the component attachment afterwards.

   WHEEL KINEMATICS (derived wheels, not in /joint_states):
     omega_i = ((vx - wz*y_i)*ux_i + (vy + wz*x_i)*uy_i) / (r_i * ux_i)  ~= (vx - wz*y_i + s_i*(vy + wz*x_i)) / r_i for 45 deg rollers
     inputs: vx, vy [m/s], wz [rad/s] = /odom twist (child frame base_footprint); omega_i [rad/s] about the wheel joint axis +Y; integrate omega_i*dt for the wheel joint position
     wheel joint               x_i [m]    y_i [m]   r_i [m] bottom roller dir (XY)    s_i
     left_front_wheel          0.09097    0.08716   0.04000   (+0.711, -0.703) -44.7deg  -1
     left_back_wheel          -0.08068    0.08696   0.04008   (+0.714, +0.700) +44.5deg  +1
     right_front_wheel         0.09097   -0.08701   0.04000   (+0.717, +0.697) +44.2deg  +1
     right_back_wheel         -0.08068   -0.08722   0.04008   (+0.712, -0.702) -44.6deg  -1
     (x_i, y_i = mean ground contact below each wheel axis in base_footprint; s_i from the measured
      direction of the roller currently at the bottom of each wheel - all rollers of a wheel share it.)

7. WARNINGS / UNRESOLVED ISSUES / DECISIONS
------------------------------------------------------------------------------
   W1. LIDAR_TYPE is read with $(env LIDAR_TYPE) and is not defined anywhere in the package. The three lidar xacros use the same mesh and position and differ only in lidar_joint yaw: MS200 = 0, LD19 = 3.1416, SCLIDAR = 3.1415926535897931. This build uses LIDAR_TYPE=MS200 (yaw 0 0 0). If your robot has another lidar, re-run the script with --lidar LD19 / SCLIDAR (or rotate lidar_frame 180 deg about its Z).
   W2. The Pro URDF (car_mecanum.urdf.xacro) has NO wheel links/joints: the four mecanum wheels are baked into meshes/pro/mecanum/base_link.stl. To allow independent wheel rotation they were split out losslessly (83509 of 155863 triangles; whole loose parts only, 29 loose parts per wheel = hub, hub cap, 9 rollers and their roller pins; motors stay in base_link). Wheel link and joint names and frames come from urdf/rosorin_old.xacro (left_front_wheel etc., declared 'fixed', axis 0 0 0 there; same chassis); here they are typed 'continuous' about +Y of the wheel frame. Geometry cross-check: wheel centroid is 0.19 mm max from the source frame axis, symmetry axis within 0.095 deg of Y, outer radius 0.0400 m. These joints are NOT in the robot's /joint_states - compute wheel spin in Unreal from the /odom twist with the mecanum equations in the WHEEL KINEMATICS section. Positive rotation about +Y rolls the robot forward on both sides.
   W3. Gripper: closed-chain linkage expressed with mimic joints. Only r_joint is independent; l_joint (x1), l_in_joint (x-1), l_out_joint (x1), r_in_joint (x1), r_out_joint (x-1) follow it. The FBX has no constraints - apply q = multiplier * q_r_joint + offset in Unreal (joint_state_publisher also publishes the mimic joints, so they may already be present in /joint_states).
   W4. URDF values are used literally, including rounded pi values (e.g. gripper_joint rpy = -3.1416 -1.5681 3.1416, l_joint rpy = 3.1416 1.5681 3.1416). This matches what robot_state_publisher computes on the robot.
   W5. Some URDF joint axes are not exactly unit length (joint1 |axis|=0.9999981, joint2 |axis|=0.9999981, l_joint |axis|=1.0000036, r_joint |axis|=0.9999983, l_in_joint |axis|=1.0000036, l_out_joint |axis|=1.0000036, r_in_joint |axis|=1.0000036, r_out_joint |axis|=0.9999979); they are normalized (as ROS/KDL does) for rotation. Literal values are kept in the ros_joint_axis custom property.
   W6. Commented-out / unused files: urdf/pro/common.urdf.xacro (back_shell_black/green links) references meshes/pro/common/back_shell_*.stl that do not exist in the package, and urdf/pro/connect.urdf.xacro defines a conflicting joint1 origin. Both includes are commented out in rosorinpro.xacro, so they are not part of the Pro model and nothing is missing.
   W7. Non-Pro chassis meshes (meshes/base_link_ack.stl, base_link_diff.stl, base_link_mec.stl) belong to the ROSOrin_Acker / _Differential / _Mecanum machine types and were not imported.
   W8. Collision geometry in the URDF is identical to the visual STLs; no separate collision meshes were exported (in Unreal use 'Use Complex as Simple' or generate convex hulls).
   W9. base_joint z = 0.025 m while the lowest base_link vertex is at z = -0.0233 m, so the model rests 1.7 mm above the base_footprint plane. Kept as-is (URDF exact).
   W10. imu_link has no visual; its URDF inertial block duplicates base_link's mass (0.8087 kg). Irrelevant for visuals, kept as an Empty frame.
   W11. URDF colours are applied as sRGB (converted to linear Base Color) on 2 shared materials; wheels use base_link's material because they were part of its visual.
   W12. On import Unreal 5.8 logs 'degenerate tangent bases' / 'nearly zero bi-normals' Display messages for the small gripper, camera and link meshes (thin CAD sliver triangles in the source STLs). They are informational only; geometry and transforms are unaffected.
